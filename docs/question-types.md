# 扩展题型

新增题型必须贯穿请求校验、提示词、答案解析、API 文档和自动化测试。不要只修改 Prompt：题型如果没有解析和校验，接口无法可靠地兑现其返回格式。

## 当前题型代码位置

- `app/models.py`：`QuestionType` 限制可接受的题型标识。
- `app/prompt.py`：`build_prompt()` 为题型选择回答说明。
- `app/parsing.py`：`parse_answer()` 将模型文本转换成服务输出，并拒绝无效答案。
- `app/main.py`：请求边界校验和成功响应。
- `tests/test_quiz.py`：答案解析、请求/响应契约。
- `docs/api.md`、根目录 `README.md`：公开题型和答案格式。

## 实施步骤

以未来添加一种题型 `example` 为例：

1. **定义输入和输出。** 明确是否需要选项、模型应该返回什么，以及 OCS AnswererWrapper 接受的答案表示。先确认不能复用现有单选、多选或判断格式。
2. **开放题型标识。** 在 `app/models.py` 的 `QuestionType` 中加入新标识。只有确有上游传值依据时才增加别名；不要接受任意未知字符串。
3. **添加专属提示词。** 在 `app/prompt.py` 中为该题型定义明确、短小的输出规范。如果需要额外题目数据，调整请求模型和提示词构造，并更新 GET/POST 参数说明。
4. **实现严格解析。** 在 `app/parsing.py` 中添加题型分支，接受预期格式并规范化为 OCS 要求的答案。不能解析、输出含糊或超出题型规则时抛出 `ValueError`，由路由返回错误；禁止将原始模型输出无条件当作有效答案。
5. **补请求校验。** 如题型依赖特殊字段或选项，使用 Pydantic 模型约束，并检查 GET 与 POST 两种输入路径一致。需要新字段时不要让 GET 悄悄丢弃不支持的值。
6. **添加测试。** 覆盖规范输出、常见格式差异、无效/含糊输出、必要输入缺失、GET/POST 成功响应和未知题型拒绝。测试模型调用应使用 mock。
7. **更新文档。** 更新 `docs/api.md` 的题型、输入和答案表示，以及根目录 README 的支持列表；若扩展步骤变化，也更新本文件。
8. **运行验证。** 执行 `uv run python -m unittest discover -s tests -v`、`uv run python -m compileall -q app tests` 和 `git diff --check`。

## 解析实现约定

- 优先从明确的标签或明确的判定词中提取结果，不从解释性文字中随意猜测。
- 选择题答案必须对应有效选项标签；对于自定义标签，验证依据应与提示词生成标签的规则一致。
- 单选题只能返回一个答案，多选题应去重并维持模型给出的顺序。
- 题型规范化应对别名和大小写保持一致，并避免把新增题型意外落入判断题的默认分支。
- 模型输出是非可信输入；解析代码必须处理空内容、额外说明和格式不完整的情况。

## 完成标准

新增题型只有在输入契约、模型提示词、答案解析、错误路径、GET/POST 测试及用户文档都已覆盖时才算完成。
